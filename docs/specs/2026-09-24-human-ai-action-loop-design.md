# 人机协作行动回合：游戏化体验设计草案

状态：分阶段实施。P0 原生读取已在开发版 Personal Panel 中核对；P1 显式关联正在实施，P2/P3 仍是设计，不应在界面上伪装已完成。本草案承接 Personal Panel 的 `docs/specs/2026-09-22-gamification-audit.md` 与 `docs/camp-actions.md`，不重建“营地”，只设计个人任务、控制台看板与 Codex 执行之间缺少的接续。

## 目标与设计边界

目标用户是会在多个会话、项目和生活领域间切换的本人。典型情境是突然想到一件事、暂时不想执行；稍后想继续，可能亲自做，也可能交给 Codex；收到结果后需要核对、保留结论或再次调整。

主要结果不是使用时长、签到天数或待办数量，而是：**中断后仍能找回准确的下一步，并能分辨任务意图、机器执行与本人验收各自进行到了哪里。** 质量约束是零意外发送、零凭标题误配、零未经确认的自动完成。若这些基础条件不成立，先修功能，不引入新奖励。

## 权威、身份与三条事实线

Anytype 原生对象保管个人目标、任务和长期关系；Codex 原生会话与队列保管消息及执行；控制台综合清单保管自己的待办任务。游戏视图只是这些事实的投影，不创建第四套任务状态。

一张“行动卡”不能只有单一状态，应并列呈现：

| 事实线 | 真实问题 | 可确认来源 | 不可推断 |
| --- | --- | --- | --- |
| 意图 | 我想推进什么、下一步是什么？ | Anytype 任务 ID／控制台清单 ID 与原值 | 标题相同就是同一任务 |
| 执行 | Codex 是否已收到、排队、运行或产出？ | 原生队列项、会话和回执 ID | 已发送等于已做完 |
| 验收 | 产物是否由我核对、可继续使用？ | 本人确认及可回访的产物引用 | 工具结束等于目标完成 |

跨系统关系必须由本人显式建立，保存双方稳定身份（Anytype 的 `accountId/spaceId/taskId`、Codex 的设备／会话／消息或运行 ID）、来源和关系确认时间。不可按标题、文本相似度自动建立关系。首个切片只有在原生关系的持久写入和读回接口明确后，才把“已关联”作为持久状态；在此之前仅提供跳转与候选预览，不假装已经合体。

## 核心玩法：可中断的行动回合

一个回合不是一个自然日，也没有必须完成的时限。它从本人决定处理某个念头开始，在留下可核对的结果或下一步时自然结束；可以无限期暂停。

1. **接住**：快速记录文字和现有附件；默认“仅保存，不发送”。反馈为“已保存到哪个来源、是否会自动执行”。不能因保存就获得完成反馈。
2. **选择**：看见任务缘由、上次停点与建议的最小下一步。本人选择“自己做”“交给 Codex”“稍后再说”或“放下”。建议只解释依据，不替本人作选择。
3. **执行**：委派时明确显示目标会话、将发送的实际内容和是否立即运行；队列暂停与人工执行保持独立。Codex 的接收、排队、运行、待输入和产出只按原生回执更新。
4. **核对**：打开真实产物或会话。本人选择“接受成果”“继续调整”“只记录学到的事”或“没有完成目标”。只有确认过的产物能成为个人任务的成果证据；拒绝结果不抹去执行记录。
5. **续接**：可选留一句“下次从这里继续”。重返时优先展示它以及来源、最近一次已确认变化；未知或失联时说“待核对”，不显示伪造进度。

### 卡片的最小布局

```text
任务名称                         [原生来源] [当前个人状态]
为什么做 / 上次停在这里（可展开）
执行：未委派／已入队／运行中／有产物／待核对
成果：尚未核对／已核对的引用与一句结论
[自己继续] [交给 Codex…] [暂停] [放下]
```

“交给 Codex…”必须打开确认步骤，呈现目标会话、实际消息和执行方式；不能把存待办、入队和立即发送压成一个默认动作。按钮文案不使用含糊的“恢复”。

## 游戏化机制与克制

以 Octalysis 的 CD1／CD2／CD3／CD4 为主，不追求八项全开：

- **意义**：任务可显示所关联的长期方向或项目；没有明确关系就不编造“主线”。
- **真实进展**：反馈“留下了可核对的产物”“确定了下一步”“排除了一个错误方案”等事件，不把发送次数或文字量当成长。
- **选择与创造**：自己做、委派、暂停、退回、放下均可成立；Codex 可以提议路线，人的选择保持可见。
- **积累与复用**：重返时让上次结论和相关经验真正减少重新理解成本。只有来源明确的关系才显示关联经验。

第一版不做 XP、排行榜、连续签到、虚构稀缺或缺席惩罚。未来若加入里程碑视觉，只能由已核对的原生事件派生，能点回证据；关闭视觉效果不影响任务功能。暂停不扣分，不清零，也不生成“拖欠”叙事。真实期限可以展示来源，但不能因没有期限而制造倒计时。

## 交互反馈与失效路径

| 情境 | 用户看到的反馈 | 下一步 |
| --- | --- | --- |
| 保存成功但未执行 | “已存待办；不会自动发送”及所属来源 | 可关闭或继续编辑 |
| 已入队但任务状态回写未确认 | “队列已收到，任务状态待核对” | 禁止盲目重复入队，刷新两个来源 |
| 执行结束但目标未验收 | “Codex 已产出；等待你核对” | 查看产物、接受或继续调整 |
| 跨系统关系写入不确定 | “关联结果未知”而非“已关联” | 只读核对稳定 ID，不自动重试写入 |
| 原生来源不可读 | 来源标记为暂不可用，保留最后已确认时间 | 手动刷新；不把旧值当当前状态 |

## 最小切片与验收门槛

**P0：可信读取。** 启动并读回 Personal Panel 的原生任务，验证安装版看板的真实卡片、来源、状态、错误提示和响应时间。当前桥接代码已有，但未运行的原生维护端仍使现场验收缺失；这一步不通过，不进入自动跨端动作。

**P1：一张显式关联的行动卡。** 先只支持本人选择一项原生任务和一个现有 Codex 会话；确认关联后读回双方稳定 ID。卡片在两个工作区都能到达同一任务与会话。撤销关联只移除关系，不删除任一原生任务或会话。跨端局部成功须显式显示，不伪装事务成功。

P1 接口约定：Personal Panel 的原生任务持有会话关联关系；控制台不复制任务正文或维护第二份关联表。关联只保存 `deviceId`、`sessionId` 和原生写入时间，不保存发送或完成状态。控制台先读原生 `task.links.inspect` 能力与 `task.listLinks` 当前关系，再按本人选中的既有会话提交 `task.linkExecution`；撤销用 `task.unlinkExecution`。所有写入包含账户与空间 owner、任务 ID、原生 revision 和明确确认。写入后再读回；不确定时保持“待核对”，禁止自动重试。原生关联属性不存在时须由本人单独初始化，不在浏览看板时暗中建 schema。控制台 HTTP 变更继续要求精确 Origin，界面不能由标题推断关联，也不能因为关联而发送消息或改变任务状态。

确认步骤呈现在当前任务卡片内：属性尚未建立时先解释影响、显示独立的“初始化关联属性”按钮；属性就绪后选择会话，再显示具体任务与会话的“确认关联／确认解除”。不得依赖可能被嵌入浏览器抑制的系统确认框。只读浏览不触发属性检查以外的写入；关联能力按需读取，避免拖慢任务清单首屏。

**P2：一次完整回合。** 用一项可恢复的测试任务演练：保存但不发送 → 确认委派 → 原生队列／会话回执 → 核对产物 → 可选留下一步 → 从另一工作区恢复。人工核对结果后才允许推进个人任务状态；机器失败也能留下有用结论。

**P3：成长视角。** 只有 P0–P2 的来源与恢复路径稳定后，才加主线／任务线／里程碑视觉；这些是对现有对象关系的地图，不是第二份任务账本。

## 观察与判停

观察一次自然使用，不设催促实验：记录从念头到安全保存是否容易、隔一段时间能否直接找回准确停点、执行和验收状态是否被误读、暂停是否产生压力。主体验成功的证据是“回来能接上并理解结果”；任务数量和打开频率上升不算成功。

若出现意外发送、重复任务、来源状态不一致、因追求进度拆碎任务，或本人开始害怕暂停，停止增加游戏化反馈，先修权威、回执和退出路径。没有真实使用观察前，本草案只是假设，不宣称提升了效率或幸福感。
